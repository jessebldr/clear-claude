## 2. Statusline — the documented surface `[DOCS]`

Source: `/en/statusline`, `/en/settings-reference`.

- **Config:** `statusLine: {type: "command", command, padding?, refreshInterval? (seconds, min 1), hideVimModeIndicator?}`.
- **When it runs:** session start/resume, each new assistant message, after `/compact`,
  permission-mode change, vim toggle, `refreshInterval` tick, when a rate-limit window
  reaches `resets_at`, when the prompt cache reaches `expires_at`. Debounced 300 ms. A new
  trigger **cancels the in-flight script**. No hard timeout is documented.
- **Failure:** non-zero exit or empty output blanks the line.
- **Output:** multiple lines, ANSI colour, OSC 8 links. stdout is captured, so read
  `COLUMNS` / `LINES` env (since 2.1.153) for width.
- **Windows:** *"runs status line commands through Git Bash when Git Bash is installed,
  or through PowerShell when Git Bash is absent."* Git Bash eats backslashes — use forward
  slashes.
- **Gates:** needs workspace trust; `disableAllHooks`, `allowManagedHooksOnly`,
  `--safe-mode` disable it silently.

### stdin fields

`cwd`, `session_id`, `session_name?`, `prompt_id?`, `transcript_path`, `version`,
`model {id, display_name}`, `workspace {current_dir, project_dir, added_dirs, git_worktree?, repo? {host, owner, name}}`,
`output_style {name}`, `cost {total_cost_usd, total_duration_ms, total_api_duration_ms, total_lines_added, total_lines_removed}`,
`context_window {total_input_tokens, total_output_tokens, context_window_size, used_percentage, remaining_percentage, current_usage {…cache tokens}}`,
`exceeds_200k_tokens`, `prompt_cache? {…}`, `fast_mode`, `effort? {level}`, `thinking {enabled}`,
`rate_limits? {five_hour?, seven_day?, spend_limit?}` each `{used_percentage, resets_at}`,
`vim?`, `agent? {name}`, `pr? {number, url, review_state}`, `worktree? {…branch}`.

Rules that shape the design:

- `rate_limits` appears **only for Pro/Max subscribers (or a spend-limit gateway), and
  only after the first API response**. Each window can be absent independently. API-key,
  Bedrock and Vertex users never get it.
- `context_window.used_percentage` and `current_usage` are **null** at session start and
  again right after `/compact`.
- **Not in stdin:** git branch / dirty / ahead-behind, permission mode, todos/tasks,
  subagent list, background shell state, active tool.

### `subagentStatusLine`

Redraws each row of the agent panel. stdin: base fields + `columns` + `tasks[]` of
`{id, name, type, status, description, label, startTime, model, effort, contextWindowSize, tokenCount, tokenSamples, cwd}`.
stdout: one JSON `{id, content}` per line; omit an id to keep the default row.

### What a plugin may ship

*"Plugins can include a `settings.json` file at the plugin root… Currently, only the
`agent` and `subagentStatusLine` keys are supported."* A plugin **cannot** register the
main `statusLine`; something must write it into the user's settings. `statusLine` is not
a `plugin.json` field either (already `[CLI]`-verified in 2.1.274).

### Plugin state and config

- `${CLAUDE_PLUGIN_ROOT}` — under `plugins/cache`, **path changes on every update**;
  "treat it as ephemeral".
- `${CLAUDE_PLUGIN_DATA}` → `<config home>/plugins/data/<id>/` (id sanitised to
  `[a-zA-Z0-9_-]`), **survives updates**, removed on uninstall unless `--keep-data`.
- Both are exported to hook, MCP and LSP processes and substituted in skill content.
  **The statusline command is not listed as receiving them.**
- `userConfig` values live in user `settings.json` under `pluginConfigs`, show as rows in
  `/config` (2.1.269+), reach hooks as `CLAUDE_PLUGIN_OPTION_<KEY>`.

## 3. Classic hooks — what is observable without Mods `[DOCS]`

32 events; handler types `command`, `http`, `mcp_tool`, `prompt`, `agent`. No function or
module type is documented. Relevant to this project:

- `PostToolUse` on Bash: `tool_response {stdout, stderr, interrupted, isImage}`, plus
  top-level `duration_ms`. **No exit-code field.**
- `PostToolUseFailure`: `error: "Exit code N\n…"`, `is_interrupt`, `duration_ms`. Docs:
  *"Key your hook on `tool_name`, `is_interrupt`, and the `Exit code N` first line."*
- `Stop` / `SubagentStop`: `background_tasks[] {id, type, status, description, command…}`.
  No event fires when a background shell finishes.
- `SubagentStart/Stop`, `TaskCreated/Completed`, `PreCompact/PostCompact`,
  `MessageDisplay` (display-only rewrite of streamed assistant text).
- Windows: exec form needs a real `.exe`; `"command": "node", "args": [...]` is the
  documented pattern.
- **Transcript JSONL:** *"The entry format is internal to Claude Code and changes between
  versions, so scripts that parse these files directly can break on any release."*

So a deterministic verification record (command finished, failed or not, when, how long)
is buildable **today on documented hooks**, with the same information the mod sees.

## 4. Function hooks — capability matrix

Shape: `hooks/hooks.json` → `{"modules": ["./register.js"]}` (one entry). The module
exports `register(on, options)`; hooks are `($, e, next)`. No DOM, no Node; every side
effect goes through `$`. A failing hook is **skipped** and the chain continues; budget
10 s per dispatch. The validator statically reports every event hooked, every `$` call
and every env var read. `[TYPES]` `[CLI]` `[RUNTIME]`

| Event / API | Observed? | In docs? | Inspect | Mutate | Deny | State | Useful here | Risk |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `session.start` | RUNTIME | no | cwd, surface | no | no | start timers | load state | low |
| `session.measure` | RUNTIME | no | context, rateLimits, cost | no | no | — | pushed usage, no polling | low |
| `session.compact` | RUNTIME (`manual`) | no | trigger, messages | instructions, messages | `{skip}` | — | compact-handoff | **high** if mutating |
| `session.end` | RUNTIME | no | reason | no | no | flush | cleanup | low |
| `prompt.submit` | RUNTIME | no | text, origin | text | `{drop}` | — | none (judgment layer) | high |
| `turn.start` / `turn.complete` | RUNTIME | no | turnId, reason, durationMs, usage | complete: extra text under answer | no | per-turn | verification summary | medium |
| `turn.step` | TYPES only | no | model request | model, effort, stream | — | — | none | high |
| `tool.call` | RUNTIME | no | tool, input, agentId, result, isError, text | input, result, context | `{deny}` | — | verification-state, hygiene | observe: low; mutate: **high** |
| `tool.check` | TYPES only | no | permission verdict | decision | yes | — | none | high |

`RenderComponent` values `[TYPES]`: `AskUserQuestion, UserMessage, AssistantMessage,
ToolUse, ToolResult, ToolGroup, ToolProgress, CommandOutput, Spinner, TurnDuration,
InfoNotice, SessionMode, PromptHint, AbovePrompt, Pane`. There is **no StatusLine
component** — the classic statusline is not hookable; `$.ui.status` and `AbovePrompt`
are the mod-side equivalents.

## 5. What this means

1. Clear UI does not need Mods. Every v0.1 field is in documented statusline stdin or one
   `git` call.
2. `verification-state` does not need Mods either: documented `PostToolUse` /
   `PostToolUseFailure` carry the same facts Spike B saw.
3. Only the **transcript activity renderer** genuinely requires Mods. It works today
   (Spike C) and must wait for a documented API.
4. Mods may eventually host Clear UI itself (`session.measure` + `$.ui.status`: no
   process spawn, no Node requirement, no settings edit). Keep the renderer a pure
   function so either host can call it.
